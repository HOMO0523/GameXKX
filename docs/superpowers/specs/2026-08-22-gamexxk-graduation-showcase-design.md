# GameXXK 毕业设计离线介绍页设计规格

> 日期：2026-08-22
> 状态：用户已批准信息架构、角色与全卡模板、视觉与离线交付、三大核心支柱、数据真源与验收口径
> 交付目录：`Deliverables/GameXXK_Graduation_Showcase/`

## 1. 目标与受众

本项目交付一套供指导老师离线浏览的中文 HTML 毕业设计介绍页。页面需要完整说明 GameXXK 的游戏定位、三大核心内容、系统闭环、角色差异、全部现役卡牌效果与数值，以及卡牌和角色的设计思路。

交付物不是答辩幻灯片，也不是运行时游戏 UI 的网页复刻。老师应能双击 `index.html` 后顺序阅读，也能通过目录、搜索、筛选和深链接快速定位任意角色、机制或卡牌。运行时不得要求联网、启动本地服务器、安装软件或执行构建命令。

## 2. 页面定位与首屏文案

浏览器标题固定为：

> GameXXK 毕业设计｜水墨作战图鉴

首屏主标题固定为：

> GameXXK

首屏副标题固定为：

> 城镇有故事，局内有策略，桌面有成长

首屏定位说明固定表达为：

> 一款融合 HD2D 城镇探索、类《杀戮尖塔》路线卡牌挑战与桌面放置刷宝提升的队伍构筑单机 RPG。

《杀戮尖塔》只作为路线节点、敌方意图和回合制卡牌挑战的类型参考。页面必须紧接着说明 GameXXK 自身的核心差异：主角、永久伙伴和任务 NPC 的牌进入同一副共享牌组，不同角色通过资源生产、条件触发和效果兑现形成接力。

## 3. 三大核心内容

卡牌公共规则与全卡目录之前，必须先用完整章节介绍以下三根主梁。

### 3.1 HD2D 城镇探索

- 说明像素角色与具有空间、光照、景深的城镇环境如何组合成 HD2D 气质。
- 介绍移动、NPC 对话、任务、招募、商店和路线入口。
- 解释城镇的设计职责：提供人物、地点和叙事目的，让角色与卡牌拥有世界来源。
- 使用当前项目已有的真实城镇截图和批准资产，不重新生成或改写用户调好的角色、PaperZD、关卡、相机或 HD2D 平面。

### 3.2 类《杀戮尖塔》局内卡牌挑战

- 介绍路线节点、普通战、精英战、首领战、敌方意图和回合制出牌。
- 介绍共享手牌、共享气力、角色各自内力、目标选择、状态、触发时点和结算队列。
- 说明主角 8 张、永久伙伴 5 张、任务 NPC 3 张的配置关系，以及最多 3 个首领卡槽。
- 解释卡牌挑战的设计职责：把队伍协作转化为可阅读、可规划、可组合的牌组语言。

### 3.3 桌面放置刷宝提升

- 介绍常驻 2D 工作台、顶部游历条、仓库、背包、装备、编队、天赋、工具与历练地图。
- 明确区分“挑战”和“游历”：挑战负责主动路线与首次通关；游历只在已通关关卡进行低耗自动刷取。
- 介绍装备品质、词缀、套装、强化和成长资源如何回流队伍配置与下一次挑战。
- 解释放置系统的设计职责：降低重复刷取的操作负担，把玩家注意力留给构筑、装备取舍和首次挑战。

三者必须形成一个明确闭环：

> 城镇提供任务、角色和解锁 → 主动挑战提供策略验证与高价值奖励 → 工作台游历提供持续刷宝与装备成长 → 成长后的队伍返回更高难度探索和挑战。

页面同时区分“项目整体内容”和“当前默认演示入口”。当前默认演示路径写为：

> 2D 工作台 → 挑战路线图 → 全屏 BattleBoard → 结算后返回路线或工作台。

HD2D 城镇作为已存在的世界与叙事内容介绍，不得被误写成当前默认启动界面。

## 4. 整体信息架构

页面按以下顺序组织：

1. 封面、摘要与关键规模数字。
2. 三大核心内容。
3. 完整游戏循环与当前默认演示路径。
4. 卡牌设计基础：资源、目标、品质、状态、伤害、治疗、触发和结算。
5. 主角设计与 36 张全卡。
6. 六职业永久伙伴设计与 108 张全卡。
7. 六名任务 NPC 设计与 24 张全卡。
8. 首领奖励设计与 5 张首领牌。
9. 跨角色构筑关系、资源生产/消费矩阵和代表性接力顺序。
10. C++ 驱动的 Slate/UMG 整体界面设计。
11. 数值校验工具、模拟对战与分层数值测试体系。
12. HD2D、美术、工程实现与制作复盘。
13. 数据来源、版本与验证说明。

全局搜索结果直接跳转到角色章节中的权威卡牌行。页面不维护第二份重复全卡表，避免同一张牌在两个页面位置产生数值漂移。

## 5. 角色章节模板

主角、每个永久伙伴职业、每名任务 NPC 都使用同一套八段模板：

1. **角色定位**：一句话体验、战斗职责、特色关键词。
2. **设计问题**：希望玩家做什么决策，解决什么职业同质化问题。
3. **机制循环**：按“资源生产 → 准备 → 触发 → 兑现”说明闭环。
4. **数值边界**：费用、倍率、层数、次数、公式和取舍。
5. **卡组分型**：核心牌、子流派，以及启动、维持、桥接、转化和终结职责。
6. **全卡效果表**：完整展示该角色所有现役候选卡。
7. **组合示例**：至少两条角色内部或跨角色的代表性接力。
8. **设计复盘**：风险、克制关系、验证数据和迭代理由。

### 5.1 角色顺序

- 主角：12 张泛用牌，然后按刀客、守卫、药师、弓手、法师、阵师各 4 张联动牌说明。
- 永久伙伴：刀客、守卫、药师、弓手、法师、阵师；每类 18 张。
- 任务 NPC：土司首领、宋金宝、月白、周光祖、金贵、琼么儿；每人 4 张，逐人解释双职业组合与 4 选 3 规则。
- 首领牌：单独设置“首领奖励设计”章节，说明黑熊获取键下的 2 张和老虎获取键下的 3 张，以及 3 个首领卡槽的取舍。

## 6. 全卡表与逐卡设计字段

每张卡的默认表格行展示：

- 编号与卡名。
- 当前基础品质和获取方式。
- 气力、内力。
- 目标模式。
- 完整效果与关键数值。
- 所属流派或机制标签。
- 循环职责。
- 逐卡设计思路。

点击或键盘展开后显示：

- CardId。
- 触发时点、条件、消耗、目标失效规则和公式。
- 未缩放目录底值、品质换算规则与当前基础品质下的局内实值。
- 资源生产端、消费端、推荐联动和风险。
- 数值依据与取舍。
- 数据来源和规则版本。

“完整效果”必须使用当前卡牌文本格式器导出的玩家可读结果。“实现签名”只用于展开后的程序核对，不进入默认正文。页面必须把未缩放底值与品质后的实值分栏并清楚命名，不能把两者混成一组数字。

逐卡设计说明是独立的设计解读层，不伪装成代码事实。每条设计解读至少包括 `designRole`、`intent`、`numericRationale`、`synergies` 和 `risks`；所有字段以 CardId 作为合并键。

## 8. 数据流与职责边界

数据分为三层：

1. **代码事实层**：`FGameXXKCardCatalog::GetAllCardDefinitions()`、品质解析和卡牌文本格式器。
2. **现役过滤层**：保留所有角色牌和 5 张 `Route.Boss.*`，排除其他路线牌。
3. **设计解读层**：按 CardId 维护角色定位、流派、逐卡意图、数值依据、联动和风险。

实施时先运行 `GameXXK.Data.CardDocumentation` 刷新 `docs/design/2026-08-11-full-card-catalog.md`，再由独立生成脚本解析目录、应用现役过滤、合并设计解读并输出 `assets/cards-data.js`。最终 HTML 本身包含所有可顺序阅读的正文和卡牌内容；JavaScript 只增强搜索、筛选、展开和深链接。

生成清单记录：

- 目录源文件 SHA256。
- 设计说明源文件 SHA256。
- 生成时间与页面版本。
- 总数和各分区数量。
- 所有 CardId 的排序后列表。
- 使用到的图片相对路径及缺失清单。

## 9. Slate/UMG 整体界面设计

介绍页必须设置独立技术章节，说明 GameXXK 并非依赖一组彼此孤立的蓝图页面，而是采用 C++ 驱动的 Slate/UMG 体系组织运行时界面。页面使用“状态—协调—界面—绘制”四层图说明：

```text
UGameXXKMVPSubsystem
  权威运行时状态、存档、卡牌战斗与历练数据
        ↓
AGameXXKMVPPlayerController
  屏幕生命周期、懒创建、ZOrder、焦点、输入模式与返回栈
        ↓
UGameXXKDesktopTrainingWorkbenchWidget
UGameXXKOneGameRouteMapWidget / UGameXXKRouteEncounterPanelWidget
UGameXXKBattleBoardWidget
  C++ 构造 WidgetTree、读取状态、刷新表现
        ↓
RebuildWidget / NativePaint / Atlas 与纹理缓存
  自定义按钮、箭头、墨线、动画层和最终 Slate 绘制
```

### 9.1 设计目标

- **确定性几何**：桌面工作台与战斗 HUD 使用 1920×1080 设计基准和 ScaleToFit 安全舞台，使布局可由纯函数和自动化验证。
- **状态与表现分离**：Subsystem 保存权威状态；Widget 只读取并呈现，不从界面文字或可见性反推玩法数据。
- **统一屏幕协调**：PlayerController 管理工作台、路线图、事件/商人、BattleBoard 的创建、层级、可见性、焦点和输入模式。
- **同地图切屏**：当前默认流程在 `L_DesktopTrainingHUD` 内关闭工作台、显示路线图或全屏 BattleBoard，退出后恢复工作台，不以加载 3D 场景作为日常切屏手段。
- **可测试的程序化树**：关键控件由 C++ 创建并拥有稳定名称、稳定槽位与测试探针，自动化可以核对 WidgetTree、按钮数量、几何、层级和状态。

### 9.2 SafeStage 与局部坐标

页面需要以目标箭头案例解释 Slate 坐标设计：

1. PlayerController 优先读取 viewport-client 的本地 DPI 坐标。
2. 指针通过 `BattleHudSafeStage` 的 `Offset/Scale` 转为 1920×1080 stage 坐标。
3. `NativePaint` 只使用 Board-local / SafeStage-local 坐标绘制。
4. 禁止 `LocalToAbsolute → AbsoluteToLocal` 跨 Geometry 往返，避免浮动 PIE 窗口的桌面原点污染局部位置。
5. 方向向量只参与旋转和法线，不参与位置平移；贴图可见箭尖使用明确 hotspot。

这个案例用来说明项目如何把视觉问题转化为可复现的坐标合同和几何自动化，而不是只展示最终截图。

### 9.3 生命周期、资源和输入

- HUD-only 启动只创建当前必需的工作台；路线图、BattleBoard、商人和其他重页面按需 ensure。
- 工作台折叠后保留顶部游历、Tab 和轻量状态；延迟释放重资源，过期异步回调通过 token 拒绝回挂。
- Atlas 与纹理缓存只保留当前表面所需资源；页面切换和销毁有明确释放边界。
- PlayerController 显式设置 UIOnly/GameAndUI、目标焦点和 ZOrder，避免多个全屏层同时抢输入。
- 背包携带、工具输入和临时选择在关闭、切页、失焦、存读档和界面销毁时统一回滚，保证 UI 操作原子性。

### 9.4 页面展示形式

Slate 章节包含：

- 一张四层架构图。
- 工作台、路线图、BattleBoard 三张真实截图及状态切换图。
- SafeStage 坐标链与箭头 hotspot 小图。
- 懒创建/折叠休眠时序图。
- 一张“设计问题—技术决策—验证方式”表格。

## 10. 数值校验工具与模拟对战体系

介绍页必须设置独立章节说明：GameXXK 的卡牌数值不是只靠手感填写，而是通过静态合同、逐卡执行、确定性对战、正交对照、统计汇总、受限建议和真实 PIE 组成分层验证体系。

### 10.1 八层验证结构

| 层级 | 工具或测试 | 解决的问题 |
|---|---|---|
| 1. 目录合同 | `CardCatalog`、`CardQuality`、`GameXXK.Data.CardDocumentation`、`CardText` | 数量、CardId、品质、费用、目标、卡文和数值换算是否一致 |
| 2. 逐卡动态执行 | 全目录可打出性、条件缺失分支、目标原子性、198×七地势矩阵 | 每张定义是否真的能在规则引擎中结算，而不只是“表里存在” |
| 3. 规则单元与集成 | 职业专项、状态、重放、反击、格挡、任务、重箭和共享队列测试 | 复杂触发时点和跨角色组合是否符合规则 |
| 4. 确定性模拟核心 | `FGameXXKCombatSimulationRules::RunScenario` | 在不另写伤害规则的前提下执行完整回合、敌方意图、自动出牌和终局检查 |
| 5. 锁定矩阵 | `GameXXK.Diagnostics.CardBalanceObservation`，2400 场 | 八个队伍/装备 cohort × 普通/精英/首领 × 100 个稳定种子 |
| 6. 正交矩阵 | `GameXXK.Diagnostics.OrthogonalBalanceObservation`，2520 场 | 只改变职业、套装、任务 NPC、地势或成长档中的一个维度，保持其他控制量相同 |
| 7. 汇总与建议 | `run_card_balance_observation.py`、`propose_card_balance_tuning.py` | 校验 CSV、聚合指标、计算置信区间并生成有界只读建议 |
| 8. 实机与发布门禁 | `ue_tdd_pipeline.py`、Automation、真实 PIE/MCP 流程 | 冷编译、界面接线、真实点击、存档、路线与表现没有因调数值回归 |

173 张现役展示口径和 198 张代码目录回归口径必须在页面中并列说明：页面只向老师展示现役 173 张，但测试仍覆盖目录中保留的 198 个定义，防止旧定义或迁移路径无声腐坏。

### 10.2 模拟对战如何工作

模拟器直接调用正式卡牌、敌人、状态、装备和路线倍率解析器，不维护另一套简化伤害公式。每个场景由稳定 seed、章节、节点类型、队伍 cohort、伙伴出生牌、装备、NPC 和地势定义；相同代码与相同 seed 必须产生相同终局、轨迹和指标。

一场模拟记录的不只是胜负，还包括：

- 回合数、剩余队伍生命和首回合死亡数。
- 主动出牌数与自动结算数。
- 气力/内力的消耗、获得和阶段末闲置量。
- 按来源与 CardId 统计的伤害、治疗和护甲。
- 状态生产与消费。
- 过杀、过量治疗、目标失效、最大自动队列深度和最大手牌数。
- 卡牌看见次数、打出次数和直接贡献。

模拟器具有无进展与僵持保护：连续决策或跨回合生命没有变化时结束场景并记录失败原因，不能以达到轮数上限冒充正常终局。

### 10.3 两套矩阵

**锁定矩阵 2400 场**用于回答“当前正式构筑在三章普通、精英、首领节点上的整体结果如何”。结构固定为八个 cohort、三个节点类型、每组 100 个 seed，并在三章等级间稳定分布。

**正交矩阵 2520 场**用于回答“胜负变化到底由哪个维度造成”。维度包括：

- Profession：永久伙伴职业。
- EquipmentSet：装备套装。
- QuestNpc：任务 NPC。
- Terrain：地势。
- Progression：章节与成长档。

同一个正交控制组使用相同的 seed、节点、伙伴出生种子和所有非目标字段，只替换当前被研究维度；测试会拒绝任何控制量偷变。

### 10.4 观测文件与统计方法

`run_card_balance_observation.py` 负责启动只读 UE Automation、收集 `cases.csv`、校验 Schema 3、精确场次数、非负指标、稳定身份字段和文件 SHA256，并输出 JSON/Markdown 汇总。调参前需要两次独立观测拥有相同 schema、矩阵、case count 和 CSV SHA，证明结果可复现。

`propose_card_balance_tuning.py` 使用 Wilson 95% 区间判断样本是否偏离目标，并只生成受限建议：

- 攻击倍率每次最多 ±15 个百分点。
- 固定值每次最多 ±2，且受当前值约 15% 约束。
- 气力每次最多 ±1。
- 内力每次最多 ±3。
- 敌方生命/攻击/防御倍率每次最多 ±10%。

建议文件是只读诊断，不自动修改 C++、卡牌目录或游戏资产。人需要先判断是职业预算、套装、NPC、地势还是成长倍率的问题，再选择是否实施；实施后重新走冷 UBT、聚焦测试、完整矩阵和真实 PIE。

### 10.5 页面中的证据与限制

页面可以引用带日期和来源的历史证据卡，例如 2026-08-11 的正式 FullMatrix 记录：2400 场全部得到终局、0 个 `MaxRounds`，2118 胜、282 负，总胜率 88.25%。该数字只能证明当时版本的终局率和总体结果，不能冒充当前版本的实时胜率。

页面必须同时显示模拟策略局限：当前 skilled/greedy 策略偏向即时收益，会低估蓄力、药方、法术任务、地势等铺垫牌；模拟是诊断仪器，不是“最终平衡已证明”的结论。若展示其他观察结果，必须同时给出源文件、版本日期、矩阵名称、case count 和是否通过确定性校验。

### 10.6 数值测试章节的页面形式

该章节包含：

- 一张从目录合同到真实 PIE 的八层漏斗图。
- 锁定矩阵与正交矩阵的结构对比。
- 一张完整模拟指标分类表。
- 一个带日期的历史证据卡和局限说明。
- 一张“发现偏差 → 正交定位 → 有界建议 → 人工评审 → 冷编译与回归”的闭环图。
- 数值工具文件名、用途和产物路径索引。

## 13. 交互与可访问性

核心交互包括：

- 固定章节目录。
- 全局搜索：卡名、角色、CardId、机制、效果文字和数值。

- 卡牌行展开与折叠。
- 每个章节、角色、机制和卡牌的 URL 锚点。
- 一键清空筛选。
- 打印/PDF 模式。

所有交互可用键盘完成，具有可见焦点、语义化按钮和表格标题。颜色不是唯一状态信号。主要面向 1440–1920px 桌面宽度，同时保证 1024px 可读；窄屏把宽表格转换为字段分组卡片。

关键正文和 173 张卡牌直接存在于 HTML 中。JavaScript 失效时仍能顺序阅读；搜索、筛选和展开属于渐进增强。

## 15. 异常处理

### 15.1 构建时失败

以下任一情况必须以非零状态停止生成：

- 现役总数不是 173。
- 5 张首领牌不全。
- 混入任一非首领路线牌。
- CardId 重复、缺失或归属不明。
- 费用、品质、目标或完整效果为空。
- 任一现役卡缺少逐卡设计说明。
- 数据源哈希发生变化但生成清单未复核。

### 15.2 浏览时降级

- 筛选无结果时显示条件摘要和清空入口。
- 图片缺失时显示固定比例占位与资产名称。
- 脚本失效时完整正文仍在。
- 指向旧 CardId 的链接进入“未纳入现役”说明，不显示空白页面。
- 打印时展开必要数据并隐藏交互控件。
