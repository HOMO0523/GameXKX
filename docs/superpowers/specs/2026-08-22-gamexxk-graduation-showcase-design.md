# GameXXK 毕业设计离线介绍页设计规格

> 日期：2026-08-22  
> 状态：用户已批准信息架构、角色与全卡模板、视觉与离线交付、三大核心支柱、数据真源与验收口径  
> 交付目录：`Deliverables/GameXXK_Graduation_Showcase/`

## 1. 目标与受众

本项目交付一套供指导老师离线浏览的中文 HTML 毕业设计介绍页。页面需要完整说明 GameXXK 的游戏定位、三大核心内容、系统闭环、角色差异、全部现役卡牌效果与数值，以及卡牌和角色的设计思路。

交付物不是答辩幻灯片，也不是运行时游戏 UI 的网页复刻。老师应能双击 `index.html` 后顺序阅读，也能通过目录、搜索、筛选和深链接快速定位任意角色、机制或卡牌。运行时不得要求联网、启动本地服务器、安装软件或执行构建命令。

## 2. 页面定位与首屏文案

浏览器标题固定为：

> GameXXK 毕业设计｜水墨作战图鉴

首屏主标题固定为：

> GameXXK

首屏副标题固定为：

> 城镇有故事，局内有策略，桌面有成长

首屏定位说明固定表达为：

> 一款融合 HD2D 城镇探索、类《杀戮尖塔》路线卡牌挑战与桌面放置刷宝提升的队伍构筑单机 RPG。

《杀戮尖塔》只作为路线节点、敌方意图和回合制卡牌挑战的类型参考。页面必须紧接着说明 GameXXK 自身的核心差异：主角、永久伙伴和任务 NPC 的牌进入同一副共享牌组，不同角色通过资源生产、条件触发和效果兑现形成接力。

## 3. 三大核心内容

卡牌公共规则与全卡目录之前，必须先用完整章节介绍以下三根主梁。

### 3.1 HD2D 城镇探索

- 说明像素角色与具有空间、光照、景深的城镇环境如何组合成 HD2D 气质。
- 介绍移动、NPC 对话、任务、招募、商店和路线入口。
- 解释城镇的设计职责：提供人物、地点和叙事目的，让角色与卡牌拥有世界来源。
- 使用当前项目已有的真实城镇截图和批准资产，不重新生成或改写用户调好的角色、PaperZD、关卡、相机或 HD2D 平面。

### 3.2 类《杀戮尖塔》局内卡牌挑战

- 介绍路线节点、普通战、精英战、首领战、敌方意图和回合制出牌。
- 介绍共享手牌、共享气力、角色各自内力、目标选择、状态、触发时点和结算队列。
- 说明主角 8 张、永久伙伴 5 张、任务 NPC 3 张的配置关系，以及最多 3 个首领卡槽。
- 解释卡牌挑战的设计职责：把队伍协作转化为可阅读、可规划、可组合的牌组语言。

### 3.3 桌面放置刷宝提升

- 介绍常驻 2D 工作台、顶部游历条、仓库、背包、装备、编队、天赋、工具与历练地图。
- 明确区分“挑战”和“游历”：挑战负责主动路线与首次通关；游历只在已通关关卡进行低耗自动刷取。
- 介绍装备品质、词缀、套装、强化和成长资源如何回流队伍配置与下一次挑战。
- 解释放置系统的设计职责：降低重复刷取的操作负担，把玩家注意力留给构筑、装备取舍和首次挑战。

三者必须形成一个明确闭环：

> 城镇提供任务、角色和解锁 → 主动挑战提供策略验证与高价值奖励 → 工作台游历提供持续刷宝与装备成长 → 成长后的队伍返回更高难度探索和挑战。

页面同时区分“项目整体内容”和“当前默认演示入口”。当前默认演示路径写为：

> 2D 工作台 → 挑战路线图 → 全屏 BattleBoard → 结算后返回路线或工作台。

HD2D 城镇作为已存在的世界与叙事内容介绍，不得被误写成当前默认启动界面。

## 4. 整体信息架构

页面按以下顺序组织：

1. 封面、摘要与关键规模数字。
2. 三大核心内容。
3. 完整游戏循环与当前默认演示路径。
4. 卡牌设计基础：资源、目标、品质、状态、伤害、治疗、触发和结算。
5. 主角设计与 36 张全卡。
6. 六职业永久伙伴设计与 108 张全卡。
7. 六名任务 NPC 设计与 24 张全卡。
8. 首领奖励设计与 5 张首领牌。
9. 跨角色构筑关系、资源生产/消费矩阵和代表性接力顺序。
10. HD2D、美术、UI、工程实现、测试、平衡观察与制作复盘。
11. 数据来源、版本与验证说明。

全局搜索结果直接跳转到角色章节中的权威卡牌行。页面不维护第二份重复全卡表，避免同一张牌在两个页面位置产生数值漂移。

## 5. 角色章节模板

主角、每个永久伙伴职业、每名任务 NPC 都使用同一套八段模板：

1. **角色定位**：一句话体验、战斗职责、特色关键词。
2. **设计问题**：希望玩家做什么决策，解决什么职业同质化问题。
3. **机制循环**：按“资源生产 → 准备 → 触发 → 兑现”说明闭环。
4. **数值边界**：费用、倍率、层数、次数、公式和取舍。
5. **卡组分型**：核心牌、子流派，以及启动、维持、桥接、转化和终结职责。
6. **全卡效果表**：完整展示该角色所有现役候选卡。
7. **组合示例**：至少两条角色内部或跨角色的代表性接力。
8. **设计复盘**：风险、克制关系、验证数据和迭代理由。

### 5.1 角色顺序

- 主角：12 张泛用牌，然后按刀客、守卫、药师、弓手、法师、阵师各 4 张联动牌说明。
- 永久伙伴：刀客、守卫、药师、弓手、法师、阵师；每类 18 张。
- 任务 NPC：土司首领、宋金宝、月白、周光祖、金贵、琼么儿；每人 4 张，逐人解释双职业组合与 4 选 3 规则。
- 首领牌：单独设置“首领奖励设计”章节，说明黑熊获取键下的 2 张和老虎获取键下的 3 张，以及 3 个首领卡槽的取舍。

## 6. 全卡表与逐卡设计字段

每张卡的默认表格行展示：

- 编号与卡名。
- 当前基础品质和获取方式。
- 气力、内力。
- 目标模式。
- 完整效果与关键数值。
- 所属流派或机制标签。
- 循环职责。
- 逐卡设计思路。

点击或键盘展开后显示：

- CardId。
- 触发时点、条件、消耗、目标失效规则和公式。
- 未缩放目录底值、品质换算规则与当前基础品质下的局内实值。
- 资源生产端、消费端、推荐联动和风险。
- 数值依据与取舍。
- 数据来源和规则版本。

“完整效果”必须使用当前卡牌文本格式器导出的玩家可读结果。“实现签名”只用于展开后的程序核对，不进入默认正文。页面必须把未缩放底值与品质后的实值分栏并清楚命名，不能把两者混成一组数字。

逐卡设计说明是独立的设计解读层，不伪装成代码事实。每条设计解读至少包括 `designRole`、`intent`、`numericRationale`、`synergies` 和 `risks`；所有字段以 CardId 作为合并键。

## 7. 当前现役全卡口径

最终页面只收录当前真实可获得的 173 张卡：

| 分区 | 数量 | 纳入规则 |
|---|---:|---|
| 主角 | 36 | 全部主角卡 |
| 永久伙伴 | 108 | 六职业各 18 张，跨出生种子均可获得 |
| 任务 NPC | 24 | 六人各 4 张，跨 4 选 3 组合均可获得 |
| 首领奖励牌 | 5 | `Route.Boss.*`，黑熊 2 张、老虎 3 张 |
| 总计 | 173 | `36 + 108 + 24 + 5` |

当前 198 张代码目录中的其余 25 张普通、地势和稀有路线牌必须排除。它们仍存在于目录定义中，但已经退出奖励、事件、宝箱和商人获取流程。

若后续规则改变现役数量，生成流程必须失败并要求人工复核本节、设计说明覆盖层和页面统计；不得静默采用新数量。

## 8. 数据流与职责边界

数据分为三层：

1. **代码事实层**：`FGameXXKCardCatalog::GetAllCardDefinitions()`、品质解析和卡牌文本格式器。
2. **现役过滤层**：保留所有角色牌和 5 张 `Route.Boss.*`，排除其他路线牌。
3. **设计解读层**：按 CardId 维护角色定位、流派、逐卡意图、数值依据、联动和风险。

实施时先运行 `GameXXK.Data.CardDocumentation` 刷新 `docs/design/2026-08-11-full-card-catalog.md`，再由独立生成脚本解析目录、应用现役过滤、合并设计解读并输出 `assets/cards-data.js`。最终 HTML 本身包含所有可顺序阅读的正文和卡牌内容；JavaScript 只增强搜索、筛选、展开和深链接。

生成清单记录：

- 目录源文件 SHA256。
- 设计说明源文件 SHA256。
- 生成时间与页面版本。
- 总数和各分区数量。
- 所有 CardId 的排序后列表。
- 使用到的图片相对路径及缺失清单。

## 9. 视觉系统

统一方向命名为“GameXXK 水墨作战图鉴”：远看像山水长卷，近看像清楚的游戏设计档案。

| 用途 | 色值 |
|---|---|
| 页面外部背景 | `#24221D` |
| 主纸张色 | `#E8D9BE` |
| 纸张高光 | `#F3E8D2` |
| 主墨色 | `#2D2A24` |
| 次墨灰 | `#776F63` |
| 木框棕 | `#6B4A2D` |
| 古金重点 | `#B7862B` |
| 朱砂章节标记 | `#A74635` |
| 松烟青绿机制线 | `#526E65` |
| 表格分隔线 | `#B5A58D` |

标题使用本地宋体回退栈，正文与表格使用本地无衬线回退栈。不得依赖网络字体。毛笔感只用于少量章节题名或印章，不用于正文和全卡表。

材质负责建立氛围，版式负责承载信息：

- 一章使用一张主要纸面，不把每个小组件都做成撕纸。
- 水墨山水用于封面和章节开场，正文降低对比度。
- 木框只用于页面外框或大型容器。
- 每个主要章节最多一枚朱砂印章。
- 古金只用于当前选中、关键数字和重要结论。
- 一个视口最多同时强调两种材质效果。

不得照搬固定 16:9 黑边、高密度三栏 HUD、空背包格、微型按钮、浅黄字压浅纸或依赖悬停才能读懂的关键信息。

## 10. 图片与媒体

页面优先使用项目已有的真实实机截图、角色图、卡牌美术、状态图标和批准 UI 资源。不得生成一张新的概念 UI 冒充实机，不得覆盖或修改用户调好的角色 sprites、PaperZD、地图、相机和 HD2D 参数。

图片需要：

- 复制到交付目录的 `assets/images/`，使用相对路径。
- 保持原始纵横比，不拉伸。
- 提供中文替代文本和来源标签。
- 对截图进行网页裁切时只裁除编辑器边框、桌面背景和无关调试信息，不改动游戏内容。
- 缺图时显示带资产名称的固定比例占位，不让布局坍塌；缺图不会隐藏对应文字和卡牌数据。

## 11. 交互与可访问性

核心交互包括：

- 固定章节目录。
- 全局搜索：卡名、角色、CardId、机制、效果文字和数值。
- 组合筛选：角色、品质、费用、目标、机制、获取方式。
- 卡牌行展开与折叠。
- 每个章节、角色、机制和卡牌的 URL 锚点。
- 一键清空筛选。
- 打印/PDF 模式。

所有交互可用键盘完成，具有可见焦点、语义化按钮和表格标题。颜色不是唯一状态信号。主要面向 1440–1920px 桌面宽度，同时保证 1024px 可读；窄屏把宽表格转换为字段分组卡片。

关键正文和 173 张卡牌直接存在于 HTML 中。JavaScript 失效时仍能顺序阅读；搜索、筛选和展开属于渐进增强。

## 12. 离线交付结构

最终目录固定为：

```text
Deliverables/GameXXK_Graduation_Showcase/
├─ index.html
├─ assets/
│  ├─ styles.css
│  ├─ app.js
│  ├─ cards-data.js
│  └─ images/
└─ 使用说明.txt
```

运行时使用纯 HTML、CSS 和原生 JavaScript。不得引用 CDN、远程图片、网络字体、分析脚本或任何远程 API。整个目录压缩为一个 ZIP 后仍可解压并双击 `index.html` 阅读。

`index.html` 持有语义化正文和静态卡牌内容；`styles.css` 只负责视觉、响应式和打印；`app.js` 只负责搜索、筛选、展开、深链接和状态恢复；`cards-data.js` 提供同源机器可读数据，避免 `file://` 下的 `fetch` 限制。

## 13. 异常处理

### 13.1 构建时失败

以下任一情况必须以非零状态停止生成：

- 现役总数不是 173。
- 5 张首领牌不全。
- 混入任一非首领路线牌。
- CardId 重复、缺失或归属不明。
- 费用、品质、目标或完整效果为空。
- 任一现役卡缺少逐卡设计说明。
- 数据源哈希发生变化但生成清单未复核。

### 13.2 浏览时降级

- 筛选无结果时显示条件摘要和清空入口。
- 图片缺失时显示固定比例占位与资产名称。
- 脚本失效时完整正文仍在。
- 指向旧 CardId 的链接进入“未纳入现役”说明，不显示空白页面。
- 打印时展开必要数据并隐藏交互控件。

## 14. 验收

### 14.1 数据验收

- 173/173 张现役卡存在。
- 分区精确为 36 + 108 + 24 + 5。
- 25 张非首领路线牌全部不存在于页面现役数据。
- 每张卡都有完整效果、关键数值和逐卡设计说明。
- 所有 CardId 唯一，所有锚点唯一。
- 生成清单中的源哈希、数量和 CardId 列表与交付包一致。

### 14.2 功能验收

- 搜索、角色/品质/费用/目标/机制组合筛选、清空、展开、深链接均通过自动化。
- 中英文、百分号、加号、层数、公式和长效果文本均能被搜索。
- 关闭 JavaScript 后可以顺序阅读全部 173 张卡。

### 14.3 离线验收

- 断网后双击 `index.html` 完整加载。
- 页面不发出任何 HTTP/HTTPS 请求。
- 从 ZIP 解压到包含中文或空格的路径后仍可使用。
- Chrome 和 Edge 当前稳定版均可离线阅读。

### 14.4 版式与视觉验收

- 1920、1440、1024 宽度无正文、导航、表格或展开内容截断。
- 打印/PDF 模式不丢卡、不拆散表头与首行，不打印交互控件。
- 真实素材不变形，正文对比度、溢出、遮挡、表格层级和窄屏布局通过截图复核。
- 视觉复核遵守项目规则，使用 Luna 视觉代理检查最终多尺寸截图。

## 15. 范围外

- 不修改 Unreal 运行时代码、卡牌规则、平衡数值、地图、关卡、角色、美术资产或存档。
- 不把介绍页部署到公网。
- 不增加登录、数据库、上传、评论、埋点或后台管理。
- 不重新设计游戏 HUD。
- 不展示已经退出获取流程的 25 张非首领路线牌。
- 不把规划中内容写成已实现功能；规划内容若必须提及，必须带“规划”标签并与当前实机内容分开。

## 16. 完成定义

只有当离线交付目录存在、173 张现役卡全部带效果/数值/设计说明、三大核心内容完整、数据与功能测试通过、多尺寸与打印验收通过，并完成 Luna 视觉复核后，才能宣称毕设介绍页完成。
