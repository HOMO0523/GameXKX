# GameXXK 新局外商店设计

日期：2026-08-05
状态：用户已确认设计，待用户确认书面规格
范围：退役旧城镇商店玩家入口，补齐新局外装备包/伙伴包商店，并接入 UI V2

## 1. 目标与边界

城镇商人交互只打开新的局外商店。旧药品货架、旧三槽装备买卖和旧背包交易窗口不再进入玩家流程。路线商店继续作为独立系统，仍使用行旅货币、卡牌与遗物商品，不改其规则或 UI。

本阶段交付：

- 六种套装装备包与一种伙伴包的固定商品目录。
- 定价、预览、确认、扣款、随机结果、仓库/伙伴候选处理和存档闭环。
- 独立新商店窗口及 UI V2 接线。
- 城镇商人、控制器与命令路由切换到新入口。
- 旧商店玩家入口不可达，同时保留必要的旧存档兼容能力。

本阶段不包含：

- 修改路线商店。
- 新增第二套通用商店框架。
- 新增套装徽记或伙伴包专用美术。
- 删除会影响旧存档迁移的 Legacy 数据结构。

## 2. 商品目录与价格

新局外商店固定展示七种商品：

| 商品 | 数量 | 单价 | 结果 |
|---|---:|---:|---|
| 破军、玄甲、青囊、追风、蚀骨、山河装备包 | 6 | 100 永久金币 | 对应套装随机一个部位的装备实例 |
| 伙伴包 | 1 | 500 永久金币 | 按现有职业池、名称唯一与保护规则生成伙伴 |

商品目录是代码中的不可变定义，不把动态货架写入存档。新游戏已有普通初始装备；首个 500 金任务奖励可选择购买五个装备包或一个伙伴包。

## 3. 装备包规则

每个装备包固定套装，随机生成武器、头部、衣甲、腰带、鞋或饰品之一。装备等级等于购买时主角等级并限制在 `1–20`。

品质概率固定为：

- 普通：70%。
- 稀有：25%。
- 珍稀：5%。

装备允许重复，不设置保底。随机结果只依赖保存的商店种子/购买序号与商品 ID；加载同一份购买前存档会得到同一结果，不能靠读档改变抽取结果。

装备实例继续使用现有 `FGameXXKEquipmentRules::CreateRolledInstance`、36 件现代装备目录、词缀目录、套装规则和 200 格权威仓库。仓库已满时不允许购买，按钮置灰并显示“背包已满”；不得扣款或推进购买序号。

## 4. 伙伴包规则

伙伴包复用现有永久伙伴职业池、名称唯一、保护规则和满员替换流程：

- 未满 12 人时，购买成功后直接加入伙伴列表。
- 已满 12 人时，购买成功后保存一个待处理候选并进入替换选择。
- 存在待处理候选时，不允许再次购买伙伴包。
- 创建候选与扣除 500 金在同一事务中提交。
- 取消候选不会退款；候选、扣款结果和购买序号均可保存。

伙伴包结果同样由保存的购买序号驱动，加载同一购买前存档得到同一候选。

## 5. 架构与职责

### 5.1 `FGameXXKMetaShopRules`

新增独立纯规则层，负责：

- 七个固定商品定义、价格和显示元数据。
- 购买可用性与预览。
- 确定性装备部位/品质或伙伴候选结果。
- 原子扣款、装备入库、伙伴加入/候选创建和购买序号推进。
- 类型化错误码与玩家可读错误文本。

规则层不创建 UMG，不加载纹理，不直接保存磁盘，也不复用旧 `BuyItem/SellItem` 商品目录。

### 5.2 `UGameXXKMVPSubsystem`

新增 Blueprint/C++ 可调用门面，提供商品视图、购买预览、确认购买和待处理伙伴状态。所有调用必须验证当前处于城镇且不存在路线/战斗锁定；规则成功后才替换权威运行时状态。

### 5.3 `UGameXXKMetaShopWidget`

新建专用全屏商店窗口，负责商品选择、详情、确认弹窗、购买结果、错误原因和伙伴替换跳转。它只调用新门面，不调用旧 `BuyItem`、`SellItem` 或 `OpenMerchantTrade`。

### 5.4 玩家入口

- 城镇商人 `F`、控制器和命令路由统一调用 `OpenMetaShopWindow`。
- `OpenMerchantTradeWindow` 保留为弃用兼容 API，但固定拒绝打开旧窗口。
- 旧城镇货架和旧背包交易模式从玩家可见路径断开。
- 路线商店继续调用现有 `PreviewRouteMerchantPurchase` / `PurchaseRouteMerchant`。

## 6. 数据与原子事务

运行时/存档增加 `NextMetaShopPurchaseOrdinal`。如现有状态没有合适的稳定种子，增加一个只在新档初始化、旧档确定性迁移的 `MetaShopSeed`；不从当前时间生成。

装备包事务顺序：

1. 校验城镇状态、商品、金币、仓库容量、购买序号和完整运行时状态。
2. 从种子、购买序号和商品 ID 解析部位、品质与装备创建请求。
3. 在运行时副本中创建装备实例。
4. 在副本中扣除 100 金并推进序号。
5. 完整校验副本，成功后一次性替换权威状态。

伙伴包事务顺序：

1. 校验城镇状态、商品、金币、无待处理候选、购买序号和伙伴状态。
2. 从种子与购买序号创建候选。
3. 未满员则直接加入；满员则保存待替换候选。
4. 在同一副本中扣除 500 金并推进序号。
5. 完整校验副本，成功后一次性提交。

任何失败均不得部分扣款、留下实例、改变伙伴列表、推进随机序号或覆盖现有候选。

## 7. UI V2

商人 `F` 打开独立全屏新商店：

- 顶部显示永久金币和关闭入口。
- 主区显示七张商品卡及价格。
- 六个装备包分别使用对应套装的武器图标作为识别图。
- 伙伴包复用 UI V2 的伙伴入口图标。
- 右侧详情区显示套装倾向、可能部位、品质概率或伙伴包规则。
- 购买前显示确认弹窗。
- 装备购买成功后展示图标、套装、部位、品质、等级、词缀和“已进入仓库”。
- 伙伴购买成功后展示伙伴；满员时直接进入现有替换界面。
- 金币不足、仓库已满、存在待处理伙伴、非城镇状态等情况置灰按钮并显示明确原因。

UI 使用已批准的 UI V2 装备图与现有伙伴入口图，不在本阶段新增美术。纯美术切图和视觉调整不使用 TDD。

## 8. 旧商店退役

旧代码不再作为可选玩家功能：

- 城镇 NPC 不再打开 `MerchantTrade` 模式。
- 玩家命令列表不再暴露旧购买/出售命令。
- 新 UI 不显示旧药品货架、旧三槽装备或出售按钮。
- 自动化把旧入口从“可购买”改为“明确不可达/拒绝打开”。
- Legacy 物品与三槽镜像仅为旧档迁移保留，不得成为新商店商品。

不直接删除旧迁移需要的数据字段，也不修改用户调过的地图、NPC 位置、相机或角色资产。

## 9. 错误处理

新商店至少区分：非法商品、非城镇状态、金币不足、仓库已满、待处理伙伴存在、伙伴状态无效、购买序号耗尽、装备创建失败、运行时校验失败和提交失败。

规则返回稳定错误码；UI 显示本地化中文原因。所有异常和资源接近 `MAX_int32` 的情况都必须原子拒绝，不能报告未到账的增量。

## 10. 验证策略

功能代码按正常 TDD 开发；用户只豁免纯美术问题的 TDD。

验证覆盖：

- 七商品目录与固定价格。
- 六套装备、六部位、70/25/5 品质边界及 1–20 等级匹配。
- 相同存档/序号结果确定，成功后序号推进。
- 金币不足、仓库满、序号耗尽和损坏状态的原子失败。
- 伙伴未满直接加入、满员候选、替换、取消不退款、候选阻断重复购买和保存往返。
- 新门面只允许城镇使用。
- 商人 `F` 打开新窗口，旧窗口固定不可达。
- 路线商店回归不变。
- UI 商品、禁用原因、确认、购买结果和伙伴替换流程。

C++ 最终验证必须保存 UE 脏包、关闭/重启编辑器后运行冷 UBT 或项目流水线；不得使用 Live Coding/Hot Reload。随后运行目标自动化与 PIE/MCP 玩家交互。纯视觉资产另外检查尺寸、透明通道、清单、哈希与视觉结果。

## 11. 完成条件

- 城镇商人 `F` 只能打开新局外商店。

- 旧药品/旧装备买卖不再有玩家可达入口。
- 路线商店功能不受影响。
