# 中文／英文接入与八语种本地化规划

范围：当前根工作区 `codex/ui-visual-optimization`。先完成简体中文和英文，架构同时预留俄语、西班牙语、巴西葡语、日语、韩语、德语。此次是现状分析与接入方案，不表示翻译资源已经完成。Tooltip 保留原 Pill 和 ItemSlot 底，语言适配围绕文字、字体和布局进行。用户要求其他语种字体先讨论，尚未导入或替换。

## 结论

项目已有部分可本地化 UI，但还没有完整的中英切换链。优先建立统一的文本来源，并把 Tooltip 的业务结构与中文句子分开；直接翻译现有字符串会破坏 Pill 识别、条件筛选和部分排版。

本轮初次盘点的源码快照范围为 `Source/GameXXK` 的非测试 C++／头文件，统计到 503 处 `FText::FromString`、414 处 `NSLOCTEXT`、994 处 `FString::Printf`、2615 个含中文的 `TEXT` 字面量。这些是调用／字面量数量，含诊断文本与重复内容，不能当成待翻译条目数或覆盖率；随后UI文字清理会改变调用数量。盘点快照在 `Saved/Codex/CardEffects-20260907/localization-inventory.json`。

在本次检查的项目路径中，没有找到项目 Localization 配置、翻译资源目录或中英语言选择设置；`DefaultGame.ini` 也没有明确的打包文化列表。不能把编辑器自身的中文界面当成游戏已经完成本地化。

## 主要问题

| 优先级 | 当前问题 | 中英切换时的影响 | 建议 |
|---|---|---|---|
| P0 | 卡名、怪物名、卡牌效果大量由中文 `FString` 生成 | 切换文化后仍显示中文，不能完整采集翻译 | 按稳定 ID 建立文本键；数值通过参数格式化 |
| P0 | Tooltip 识别“品质：”“费用：”“阵赏·炎法”等中文字符串 | 英文会失去 Pill、分组或分支筛选 | 用结构化行描述目标、效果、关键词、数值，最后才生成语言文本 |
| P0 | 规则语义仍有待定项 | 翻译会把不一致扩散到两种语言 | 先明确任务次数和两张待定卡的规则，再锁定词条 |
| P1 | `CompactBody`、`ExpandedBody` 等缓存为 `FString` | 运行时切语言后可能继续显示旧文本 | 语言改变时统一清理、重建缓存，或保留 `FText` 格式化历史 |
| P1 | 敌方意图保存了 `CardDisplayName` 字符串 | 中途切语言／读档后，当前意图可能保留旧语言名称 | 战斗数值快照保留；名称通过意图 ID、阶段 ID 重新查询 |
| P1 | 固定卡名宽度、费用窄栏、中文单位后缀 | 英文技能名、资源名、Stack/Stacks 易溢出 | 图标＋数值；文本与序号分开；设置最小／最大宽度并实际测量 |
| P1 | 当前优先按字符数选择 Tooltip 宽度 | 同样字数的中文与英文实际占宽不同 | 中英同时接入时，按真实字体测量结果与行数选择宽度 |
| P1 | 尚无完整语言加载和 Cook 验证 | 编辑器能显示不等于 Development 包中有翻译 | 设置目标文化、资源加载策略和打包验证 |
| P2 | 字体、字距与英文长词尚未专项验收 | 标题风格不一致或自动缩到过小 | 中文标题保留江湖体；为英文明确字体与回退规则 |

当前意图栏把“敌方”和“1P”分为独立行。按用户追加反馈，状态行采用“名称 → 数值 → 原状态图标”，各列独立适配。这减少了文字长度对布局的影响，但不能代替完整本地化。

对项目现有江湖体 TTF 的字形映射做了只读检查：英文字母大小写、0～9 和常用英文标点均有字形。基本英文无需因缺字立即换掉标题字体；英文长词、字距和混排效果仍需实拍检查。证据为 `Saved/Codex/CardEffects-20260907/localization-font-coverage.json`。

## 文本接入方式

建议保持所有存档键、卡牌 ID、装备 ID 和状态枚举不变。项目文档已经要求显示名不作为存档主键，这一点继续保留。

固定按钮、标题和操作提示可以使用稳定的 `NSLOCTEXT` 或 String Table 键。卡牌效果则应保留“触发条件／目标／效果／数值／限制”的结构，让中文和英文分别决定语序，避免逐词拼接中文句子的翻译。

例如，同一条规则的数据表达为：`Damage(target, amount)`，中文生成“造成 {Amount} 点伤害”，英文生成“Deal {Amount} damage”。一次性、仅主动牌、排除来源角色等限制作为明确字段保留；不要在简述过程中按中文短句直接删除它们。

`FText` 支持文化变化和格式化历史；转换为 `FString` 会丢失这些信息。因此，现有动态字符串需要明确的重建机制。[UE 文本本地化文档](https://dev.epicgames.com/documentation/en-us/unreal-engine/text-localization-in-unreal-engine)

## 接入顺序与验收

1. 固定术语和稳定文本键，整理需要翻译的玩家文本；调试日志单独标记。
2. 优先改造 Tooltip 的结构化数据和分支选择；保留现有 Pill 外观与 ItemSlot 底。
3. 做一条完整中英流程：语言设置 → 桌面 → 背包／编队 → 战斗 → 奖励 → 返回。之后再覆盖商店、天赋、任务、事件与开发面板。
4. 按 173 张卡、419 个品质版本、36 条分支，以及怪物阶段和装备词缀逐项检查参数一致。不要只检查“英文字符串存在”。
5. 检查运行时切换、重新启动、旧档恢复、长卡名、最大数值、单复数、混合语言和缺失翻译回退。字体与界面需要真实截图；不能只看导出的翻译表。
6. 核验打包后的两种语言资源，确认默认地图仍为纯 2D 桌面流程。

推荐先完成上述完整流程的小范围接入，再扩大翻译覆盖。当前不建议直接对全部中文做自动替换。

## 字体候选：保留笔意，同时保证规则易读

江湖体继续用于中文／英文标题、按钮和突出数值。用户已说明其支持范围为中文与英文；此次基本拉丁字形检查不代表俄语、带重音拉丁字母或日韩字形也可用。其他语言应整段选择对应字体，避免只有缺字才切字体导致笔画和基线混杂。

以下是基于字体官方说明和覆盖元数据整理的**候选方案，尚未做项目内视觉定稿**。同一字重在不同字体中的视觉大小并不相同，最终需按实际卡名和最小 HUD 比例校准。

| 语言 | 标题／短按钮候选 | 长技能正文候选 | 推荐理由与待检查项 |
|---|---|---|---|
| 俄／西／巴西葡／德 | **Lora SemiBold / Bold** | Noto Sans；可对比 Noto Serif | Lora 有书写笔意，覆盖 Cyrillic、Latin Extended；优先验证俄文字形、重音、长词和数字 |
| 日语 | **Yuji Syuku**；备选 Noto Serif JP | Noto Sans JP | Yuji 是书法字形，适合短标题；复杂长规则用更清楚的正文字体 |
| 韩语 | **Nanum Brush Script**；备选 Noto Serif KR | Noto Sans KR | 保留毛笔感；最小尺寸下的笔画密度需实测，读不清时标题也使用备选 |
| 中／英 | **现有江湖体** | 沿用现有易读正文方案并验证英文 | 保持已确认的视觉风格；英文长卡名不能无限缩字 |

官方依据：[Lora 设计说明](https://raw.githubusercontent.com/google/fonts/main/ofl/lora/DESCRIPTION.en_us.html)与[覆盖元数据](https://raw.githubusercontent.com/google/fonts/main/ofl/lora/METADATA.pb)、[Yuji Syuku 设计说明](https://raw.githubusercontent.com/google/fonts/main/ofl/yujisyuku/DESCRIPTION.en_us.html)与[元数据](https://raw.githubusercontent.com/google/fonts/main/ofl/yujisyuku/METADATA.pb)、[Nanum Brush Script 设计说明](https://raw.githubusercontent.com/google/fonts/main/ofl/nanumbrushscript/DESCRIPTION.en_us.html)与[元数据](https://raw.githubusercontent.com/google/fonts/main/ofl/nanumbrushscript/METADATA.pb)。三者元数据均标记 OFL；最终选定时保存对应版本的许可证、来源、文件哈希。

Noto CJK 提供语言专属字形版本。日语汉字需要日文字形，韩语文本也应选 KR 版本，不能用中文字体的可见字形代替语言适配。[Noto CJK 官方说明](https://github.com/notofonts/noto-cjk/blob/main/Serif/README.md)

我的倾向是“**标题有笔意，正文优先清楚**”。界面统一依靠纸底、墨色、图标和排版比例，不要求每种文字都模拟同一种中文毛笔字。先做独立字样对比供用户选方向；确认字体后再导入项目，使用相同真实界面、相同内容密度、50%／75%／100% HUD 和实际打包程序截图验收。

## 准确又像玩家用语的翻译流程

卡名可以保留江湖意境，机制句必须直接说明操作和结果。不要为仿古而把规则写成谜语，也不要把后台枚举或中文四字词逐词音译给玩家。尤其不能把“冲锋”与“蓄力”都翻成 Charge，或把“护甲”“守卫”“援护”混成同一个词。

每个术语条目应同时保存：稳定键、中文定义、各语言正式译名、禁用近义词、上下文截图、可执行例子和规则版本。英文可以辅助跨语言审校，但所有语言都必须能回查中文规则和运行时证据，避免多层转译累积误差。

翻译前给每张卡整理相同的语义字段：

| 字段 | 必须保留的内容 | 典型漏译风险 |
|---|---|---|
| 触发 | 首次、回合开始、命中、结束回合等 | 把“每回合首次”变成“每次” |
| 对象与来源 | 自身、目标、全体、最高攻击友方、其他角色 | 把来源攻击误写成持有者攻击 |
| 数值与单位 | 基础值、百分比、层数、次数、气力、内力 | 将 30 点中毒误译成 30 层或 30% |
| 顺序 | 先获得再消耗、伤害后附加、重放的先后 | 相同句子换序后改变玩法理解 |
| 限制与重置 | 仅主动牌、一次性、本回合、本局、任务重置 | 简述删除限制，或误称永久增长 |

例如“本回合，其他角色的下一张主动牌气力消耗减少 {Amount}。仅生效一次。”可用英文草稿：`This turn, the next active card played by another character costs {Amount} less Energy. Triggers once.` 最终句子由审校者按游戏习惯精简，但不能丢失时限、排除来源角色、主动牌范围及次数。参数由程序注入，不由译者重新录入数值。

推荐验收链：**中文语义冻结 → 术语表 → AI 辅助初稿 → 母语且熟悉卡牌游戏的审校 → 游戏内试玩审校 → 参数自动核对**。AI 的回译与一致性检查可帮助发现问题，不能代替母语审校或玩法验证。

俄语需要验证 0／1／2／5／11／21 等数量变化；西／葡／德需避免名词性别、格和词形被碎片拼接破坏；日／韩要检查语序、标点禁则和助词。整句格式化与数量分支必须保留上下文，禁止靠 `{数字}+固定后缀` 处理所有语言。

优先构建以下自动检查：参数名称／类型完整、数字与百分比未改变、条件与限制字段齐全、术语键一致、未翻译文本可追踪、所有语种的字体覆盖。再使用真实运行时样例检查最长卡名、最大值、三类 DoT、多个状态、四分支任务、动态切语言与旧档恢复。伪本地化用于布局压力检查，不应当作正式翻译质量验收。
